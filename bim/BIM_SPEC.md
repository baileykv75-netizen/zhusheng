# 筑生样板楼 BIM 原型规格

## 1. 文档目的

本文档定义“筑生：一栋房子一生的 AI 智能体”所使用的最小可信 BIM 样板楼。模型用于验证建筑空间、构件、建造证据、运营事件和智能体动作之间的关联，不作为实际设计、审图、施工或验收依据。

模型名称：

> 筑生样板楼 ZS-DEMO-001

核心原则：

> 建立整栋建筑的可计算骨架，只将 16 层 1602 户卫生间做成精细、可运行的全生命周期垂直切片。

## 2. 真实性边界

- 建筑、户型、构件尺寸和事件数据均为工程逻辑合理的合成演示数据。
- 所有对外画面、模型和报告必须标注“脱敏合成演示模型，不作为施工依据”。
- 不得将模型描述为已经部署于真实项目。
- 不声称模型已经满足完整建筑、消防、给排水、无障碍或地方设计规范。
- 后续若引入真实资料，应保留来源、授权和脱敏说明，并单独校核。

## 3. 技术基线

| 项目 | 约定 |
|---|---|
| BIM 标准 | IFC4 |
| 主文件 | `ZS-DEMO-001.ifc` |
| 参数源 | `building-spec.json` |
| 生成方式 | Python + IfcOpenShell |
| 推荐 IfcOpenShell | 0.8.5 |
| 长度单位 | m |
| 角度单位 | degree |
| Web 模型 | 后续阶段导出 GLB |
| 属性交换 | IFC Property Set + JSON |
| 稳定身份 | 业务 ID 与 IFC GlobalId 均须跨重新生成保持稳定 |

`building-spec.json`是尺寸和业务参数的唯一事实源。生成脚本中不得重复散落建筑尺寸。

## 4. 模型范围

### 4.1 整栋建筑骨架

- 一处合成场地；
- 一栋 18 层 MiC 模块化住宅；
- 1 层为入口和公共服务空间；
- 2—18 层为标准住宅层；
- 每个标准住宅层 4 户；
- 中部设置公共走廊、楼梯、电梯和管井空间；
- 标准层允许通过程序复用同一几何模板；
- 不要求为每户建立家具、机电末端或精细装修。

### 4.2 重点垂直切片

重点对象为：

```text
ZS-DEMO-001
└── 16层
    └── 1602户
        └── 卫生间
```

精细范围包括：

- 1602 户内部主要空间；
- 1602 卫生间墙、门、楼板、防水区域；
- 冷热水支管；
- 关键接头；
- 局部关断阀；
- 微流量水表；
- 湿度传感器；
- 施工、验收、运营、维修和验证记录。

1602 卫生间渗漏是唯一完整事件。不得借本模型继续横向增加电梯、消防、安防、节能或其他故障案例。

## 5. 建筑总体参数

| 参数 | 数值 |
|---|---:|
| 建筑层数 | 18 |
| 标准层层高 | 3.0 m |
| 建筑主体宽度 X | 27.2 m |
| 建筑主体进深 Y | 14.8 m |
| 公共走廊宽度 | 2.0 m |
| 标准层户数 | 4 |
| 典型户型模块尺寸 | 11.2 m × 6.4 m |
| 典型户型目标面积 | 约 72 ㎡ |

总体坐标约定：

- 原点位于建筑首层西南角；
- X 轴向东；
- Y 轴向北；
- Z 轴向上；
- 每层标高由`(层号 - 1) × 3.0 m`计算。

## 6. 标准层平面逻辑

标准层由四个住宅模块、中央公共走廊和核心筒组成。

| 户号尾号 | 方位 | 模块区域 |
|---|---|---|
| 01 | 西北 | X=0.0—11.2，Y=8.4—14.8 |
| 02 | 东北 | X=16.0—27.2，Y=8.4—14.8 |
| 03 | 西南 | X=0.0—11.2，Y=0.0—6.4 |
| 04 | 东南 | X=16.0—27.2，Y=0.0—6.4 |

公共区域：

- 公共走廊：Y=6.4—8.4；
- 核心筒与竖向交通位于 X=11.2—16.0，并分成走廊南北两个概念空间；
- 南核心筒：X=11.2—16.0，Y=0.0—6.4；
- 北核心筒：X=11.2—16.0，Y=8.4—14.8；
- 两段核心筒之间为公共走廊，空间边界不得重叠；
- 管井布置在核心筒与湿区相邻位置；
- 1602 户位于 16 层东北模块。

该平面用于建立可计算空间关系，不要求达到建筑方案设计深度。

## 7. 1602 户空间

1602 户模块全局起点：

```text
X = 16.0 m
Y = 8.4 m
Z = 45.0 m
```

1602 户使用局部坐标描述内部空间，局部原点位于该户西南角。

| 空间 | 局部起点 X/Y | 尺寸 X/Y | 备注 |
|---|---|---|---|
| 卫生间 | 0.3 / 0.3 | 2.4 / 1.8 | 靠近核心筒和管井 |
| 厨房 | 2.9 / 0.3 | 2.6 / 2.2 | 湿区集中 |
| 次卧 | 0.3 / 2.7 | 3.2 / 3.4 | 演示空间 |
| 主卧 | 3.7 / 2.7 | 3.6 / 3.4 | 演示空间 |
| 客餐厅 | 7.5 / 0.3 | 3.4 / 5.8 | 演示空间 |
| 入口与交通 | 5.7 / 0.3 | 1.6 / 2.2 | 连接公共走廊 |

空间边界之间允许保留墙体和交通余量。第一阶段只需建立清晰、无重叠的概念空间与主要隔墙。

## 11. 分阶段实施

### 阶段 1：建筑空间骨架

实现：

- 项目、场地、建筑和 18 个楼层；
- 标准层四户、公共走廊和核心筒空间；
- 16 层 1602 户主要空间；
- 1602 卫生间主要墙体、楼板和门；
- 稳定业务 ID 与 GlobalId；
- IFC 生成、验证和使用说明。

不实现：

- 给排水管线；
- 阀门、水表和传感器；
- 防水层细部；
- 生命周期证据；
- 渗漏诊断；
- GLB 导出；
- 网站接入。

### 阶段 1.1：可识别建筑实体壳体

在不改变阶段1空间语义与稳定身份的前提下补充：

- 18块按楼层归属的结构楼板；
- 按楼层拆分的外围护墙和中央核心筒墙；
- 南北主要立面的重复型`IfcWindow`；
- 首层住宅主入口`IfcDoor`；
- 屋面板与简单女儿墙；
- 高透明度空间分析样式和1602实体定位样式。

全部新增尺寸、显示参数与业务ID规则以`building-spec.json`为唯一事实源。阶段1.1仍不得创建管线、阀门、水表、传感器、防水层、事件数据、GLB或网站联动。

### 阶段 2：卫生间构件与系统

实现卫生间防水区域、冷水构件链、独立热水支管、湿度传感器及构件拓扑。使用`IfcDistributionSystem`、`IfcDistributionPort`和`IfcRelConnectsPorts`表达系统、端口归属与方向连接，并从实际IFC自动生成建筑记忆种子和关系查询结果。

阶段2只定义构件、系统、证据要求和授权规则，不创建传感器时间序列、渗漏诊断结论、已授权动作、维修工单或生命事件状态机。

### 阶段 2.5：1602卫生间数字样间

在同一空间尺寸、建筑坐标、业务ID、GlobalId和构件拓扑下，由实际IFC身份和`building-spec.json`生成可编辑`.blend`、可网页接入`.glb`及节点manifest。新增马桶、洗手盆、淋浴设备、地漏和淋浴隔断五个IFC环境构件；镜面、灯具和饰面等非业务对象仅属于视觉层。

场景提供居住、诊断、施工记忆和维修四种视图，以及`DRY`、三级潮湿、`REPAIR_OPEN`和`REPAIRED`六种中立视觉状态。阀门视觉状态默认为`OPEN`；展示`CLOSED`不等于获得授权。证据锚点只保存位置和关联业务ID，不包含虚假证据内容。

阶段2.5不得创建事件事实、诊断结论、传感器时序、已授权动作、维修工单、AI或网站联动。IFC始终是工程语义真源，视觉模型不得成为第二套业务数据。

### 阶段 3：可执行建筑生命事件引擎

以阶段2建筑记忆种子和阶段2.5视觉manifest为只读事实源，实现可变化、可缺失、可矛盾的传感器观察与人工证据输入。通过通用拓扑、透明规则、可信等级、状态守卫、事件级人工授权、只追加审计日志和确定性重放，输出候选原因、补证建议、模拟动作建议及结构化视觉指令。

阶段3只实现独立TypeScript领域逻辑，不修改IFC、Blend、GLB和现有网站页面，不连接真实设备，不调用大模型API。规则分值只用于候选排序，不描述为真实故障概率。

### 阶段 4：网站与三维展示接入

将阶段3事件结果和视觉指令接入现有Next.js工作台与GLB显示层。恢复隐藏视觉状态时必须同时处理manifest记录的缩放、位置和材质状态，不能只设置`visible=true`。

### 阶段 5：试点数据与企业反馈

在获得真实项目授权、脱敏与校核后，验证施工证据、运营观察、维修结果和企业标准反馈；不得将合成演示结果包装为真实项目成果。

任何阶段不得提前混入下一阶段的大量功能。

## 13. 阶段 1 验收标准

### 13.1 可复现

在全新Python环境中可以按README完成：

```bash
python -m pip install -r bim/requirements.txt
python bim/scripts/generate_ifc.py
python bim/scripts/validate_ifc.py
```

### 13.2 IFC结构

- 存在且仅存在一个`IfcProject`；
- 存在一个`IfcSite`；
- 存在一个`IfcBuilding`；
- 存在18个`IfcBuildingStorey`；
- 所有空间能够追溯到对应楼层；
- 1602卫生间可以通过业务ID精确查询；
- 1602卫生间位于16层和1602户语义范围内；
- 主要墙体、楼板和门具有有效几何；
- 单位为米制；
- 模型可在Bonsai 0.8.5中打开。

### 13.3 身份稳定性

连续生成两次模型后：

- 同一业务对象的业务ID不变；
- 同一业务对象的IFC GlobalId不变；
- 不因对象创建顺序变化产生身份漂移。

### 13.4 边界

- 阶段1不得创建管线、阀门、水表或传感器；
- 不得接入大模型API；
- 不得改动现有网站业务状态机；
- 不得声称模型可用于实际施工。

## 14. 人工检查清单

使用Bonsai打开`ZS-DEMO-001.ifc`后检查：

- 楼层方向和标高是否正确；
- 标准层是否存在四户和公共区域；
- 1602是否位于16层东北区域；
- 1602内部空间是否无明显重叠；
- 卫生间是否靠近核心筒和管井；
- 墙体、楼板和门是否可被单独选择；
- 选中对象时能否读取`BusinessId`；
- 模型是否存在明显飞离原点或尺度异常。

阶段1必须完成人工检查后，才能开始卫生间管线建模。
