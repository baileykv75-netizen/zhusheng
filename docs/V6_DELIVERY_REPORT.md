# 筑生 V6 最终交付报告

## 1. 产品变化

### Before

- 1602 技术闭环很完整，但首页、住户端、实验台和集团台同时争夺注意力。
- 评委需要先理解状态码、规则、工具和工作台，才知道产品在解决什么。
- 住户、物业和专业诊断职责混在同一页面。

### After

- 首页让建筑成为界面，从整栋楼直接下钻至 16 层、1602 和卫生间。
- `/events` 先回答“一栋楼正在发生什么”，再把唯一完整深链交给 1602。
- 住户、物业、工友和集团按真实职责拆分。
- 产品显式拥有 Event Summary、BuildingTask 和 Evidence 三层模型。
- 1602 用五段状态守卫连接原确定性引擎，不另造演示状态机。

## 2. 视觉变化

- 首页改为深色 Cinematic Digital Twin：暖灰建筑体、克制发光窗、中建红单一强调。
- 概念不再拆成五个小能力名词，而通过三段建筑生命结果表达：建造不失忆、居住有回应、经验会生长。
- 1602 验证舱采用“暖白叙事 + 深色模型 + 事实卡”的双层结构。
- 五张合成证据按时间纵向排列，形成施工—异常—水表—维修—复验的连续关系。
- 技术状态、BusinessId、规则、哈希和审计默认折叠。

## 3. 页面变化

| 页面 | 核心任务 | 当前主要操作 |
|---|---|---|
| `/` | 理解筑生并定位到1602 | 进入建筑 / 进入1602 |
| `/events` | 判断整栋楼有哪些事件需要处理 | 进入所选事件的唯一任务 |
| `/worker` | 留下可被未来调用的施工事实 | 人工确认正式记录 |
| `/resident` | 报告现象、补证、授权、看结果 | 当前缺口对应的一个操作 |
| `/property` | 诊断、隔离、维修、复验 | 按事件状态给出唯一下一步 |
| `/case-1602` | 理解同一事件的五段生命线 | 进入当前已解锁章节 |
| `/group` | 审查已验证经验是否值得试点 | 人工选择试点 / 补证 / 暂缓 |

## 5. AI 资产

五张主时间链合成证据位于 `public/assets/demo-evidence/`：

1. `1602-construction-cold-water-joint.webp`：施工期接头安装。
2. `1602-resident-damp-wall.webp`：北侧墙角潮湿。
3. `1602-water-meter-observation.webp`：无人用水时的水表人工观察。
4. `1602-repair-open-wall.webp`：局部接头维修记录。
5. `1602-post-repair-wall.webp`：恢复供水后的新观察。

另有 `property-joint-inspection.webp` 用于物业检查示例。所有图片都标记 `AI_GENERATED · DEMO_SYNTHETIC`，不作为真实项目照片、视觉识别结果或施工依据。

每条正式证据同时显示或可展开核验：提交人、时间、事件、空间、构件、类型、来源和 `dataClass`。维修记录必须先选择维修照片；维修后复验必须再选择一张新的观察照片，不能复用首轮记录替代新观察。

## 6. 产品数据流

```text
工友原始记录
  → AI结构化建议
  → 人工确认的正式施工证据
  → 建筑记忆 / 空间 / 构件身份
  → 住户现象与人工观察
  → 确定性事件引擎排序候选
  → 住户独立授权
  → 物业明确执行隔离
  → 维修记录
  → 独立恢复授权与执行
  → 新观察复验
  → RESOLVED 或 REOPENED
  → 单事件经验卡
  → 集团人工评审
  → 最多 PILOT_ONLY
```

Building Agent 只负责把普通语言整理成待确认草稿、调用只读工具并解释已经验证的结果；它不能越过上述数据流。

## 7. 安全边界

- 不修改 IFC、建筑记忆种子、领域规则、双授权、审计链或集团治理守卫。
- UI 和 3D 状态不能直接推进事件状态。
- 关阀/开阀的“批准”与“执行”分离。
- 维修后必须提交新的有效观察；持续异常进入 `REOPENED`。
- `REOPENED` 会生成新的复检任务，并保留第一轮维修记录和第一轮复验引用，不覆盖历史。
- AI 不批准授权、不操作设备、不关闭事件、不自动形成企业标准。
- 工友证据贡献不用于单事件追责、处罚或排名。
- 浏览器不保存 API Key；公网第一版不部署 DeepSeek 网关。

## 9. 已知限制

- 当前是脱敏合成演示，不连接真实建筑、住户、物业或设备。
- 只有 1602 具备完整领域闭环；其余事件是结构演示数据。
- Hero 没有单独高精度 GLB，1602 也未另做 Premium GLB。
- 浏览器上传只在当前设备预览；刷新恢复依赖 `sessionStorage`，没有服务端数据库。
- 静态 GitHub Pages 不运行 DeepSeek 网关或任何服务端密钥。
- 生产 Pages 更新必须在用户授权后将功能分支合并到 `main`。

## 10. 推荐演示路径

1. 首页观察整栋建筑并聚焦 16F / 1602。
2. 进入 `/events`，说明整栋楼有 5 个事件但只有 1602 深链完整。
3. 进入 `/case-1602`，先展示施工期证据如何在入住后被重新调用。
4. 打开 `/resident`，补充墙面照片与水表人工观察。
5. 进入 `/property`，展示建造记忆、候选诊断、住户授权与物业执行分离。
6. 完成维修记录、恢复供水授权和新的维修后观察。
7. 回到 `/case-1602` 查看五阶段解锁和维修视觉状态。
8. 进入 `/group`，强调单事件只能经人工审批形成 `PILOT_ONLY`。

最终应让评委得到一个判断：外层像可交互的建筑短片，内层是一套真实、可解释、有授权边界的建筑生命事件系统。
